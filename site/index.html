01 · Problema

El consenso no es gratis, y no todos cuestan lo mismo

Las comparaciones existentes mezclan entornos, cargas y redes distintas, o usan datos de cadenas en producción donde nada se controla. Faltaba un banco de pruebas común.

Criterios heterogéneos

Los estudios de desempeño usan métricas y entornos distintos; no se identificó un benchmark estandarizado que compare PoW, PoS y PBFT en condiciones idénticas.

Datos de producción

Bitcoin o Ethereum no permiten fijar carga, número de nodos ni condiciones de red: no sirven para aislar el efecto del algoritmo.

Energía fuera del foco

Simuladores como BlockSim, SimBlock o Hyperledger Caliper no integran un modelo energético junto con la comparación bajo una misma configuración.

Hipótesis

PBFT y PoS consumen, por transacción confirmada, estadísticamente menos energía que PoW y mantienen mejores tasas de éxito bajo condiciones de red controladas y reproducibles (α = 0.05).

02 · Arquitectura

Seis capas, una interfaz común

Los tres algoritmos implementan el mismo contrato ConsensusModule (start · submit_transactions · get_metrics · stop). El orquestador no sabe qué algoritmo ejecuta.

  1. 0

    Entrada

    CLI (Click) · dashboard Flask · experiment.yaml declarativo

  2. 1

    Orquestador

    ScenarioRunner · DockerManager · NetworkController (Pumba / tc-netem) · bloqueo exclusivo de ejecución

  3. 2

    Consenso

    PoW SHA-256 propio · PoS por ranuras con Ed25519 · PBFT Castro & Liskov

  4. 3

    Monitoreo

    EnergyEstimator (proxy CPU·TDP) · ResourceMonitor · TxTracker · NetMonitor

  5. 4

    Almacenamiento

    SQLite · CSV crudo · snapshot JSON por UUID · logs por nodo · hashes SHA-256

  6. 5

    Análisis

    Shapiro-Wilk → Kruskal-Wallis · Mann-Whitney + Holm · delta de Cliff · bootstrap

03 · Protocolo experimental

90 ejecuciones, ninguna descartada

Nueve grupos de diez repeticiones con orden aleatorizado por bloques (semilla 20261014). Las ejecuciones fallidas se conservan y cuentan en la energía.

Escenarios

3 algoritmos × {3, 4} nodos, más barrido de dificultad PoW 14/16/18/20 bits con 3 nodos.

Carga

100 transacciones a 50 TPS. Bloques de 20 tx y 1 confirmación (PoW/PoS); ranuras PoS de 0.5 s.

Red emulada

50 ms de latencia sin jitter, 10 Mbps y 0 % de pérdida, aplicados con Pumba y verificados en cada nodo.

Trazabilidad

Imágenes fijadas por digest, código con hash SHA-256, snapshot de configuración y logs por corrida.

Confirmación

Una transacción cuenta cuando al menos 2f + 1 nodos la confirman, con f = ⌊(n − 1)/3⌋ (quórum 1 con 3 nodos, 3 con 4). Es una convención de observación, no equivalencia de seguridad.

Ventana

La observación se cierra 5 s después del envío (~7.1 s). Con 100 tx el throughput máximo observable es ~14.1 TPS: no mide capacidad máxima.

Clasificación

Cada ejecución es cero, parcial o completa según las transacciones confirmadas por quórum.

05 · Barrido de dificultad

PoW: mismo gasto, menos confirmaciones

Con 3 nodos, la energía por ejecución se mantuvo casi constante entre dificultades; lo que cambia es cuántas transacciones logran confirmarse con ese gasto.

06 · Análisis estadístico

Pruebas no paramétricas con corrección múltiple

Shapiro-Wilk rechazó normalidad en varios grupos, así que la comparación global usa Kruskal-Wallis y los pares Mann-Whitney con corrección de Holm sobre 18 comparaciones; el tamaño del efecto es el delta de Cliff.

Conclusión

Los resultados respaldan la hipótesis: PBFT y PoS consumieron significativamente menos energía que PoW en ambos tamaños de red, y completaron más ejecuciones. También aparecen trade-offs: PoS tuvo el menor costo pero una ejecución sin progreso en cada tamaño; PBFT fue el más estable con 3 nodos pero no completó la carga en ninguna ejecución con 4.

07 · Alcance

Lo que estos datos no dicen

La energía es un estimador basado en CPU y TDP, no una medición con hardware; no incluye incertidumbre sistemática del modelo.

Solo redes de 3 y 4 nodos en un único equipo, con carga fija y red emulada. n = 5, 7, saturación, ataques y VPS son trabajo futuro.

Con 3 nodos PBFT tiene f = 0 y quórum de una réplica: su baja latencia no evidencia tolerancia bizantina.

Son implementaciones simplificadas en Python (PBFT sin cambio de vista ni checkpoints; PoS sin slashing), no las de plataformas en producción.

La observación se cierra 5 s después del envío; el throughput no representa capacidad máxima.

No se identificó la causa del colapso de PoW con 4 nodos ni de las ejecuciones sin progreso de PoS.

08 · Reproducibilidad

Corre el framework

Requiere Python 3.13 y Docker. El repositorio incluye la base SQLite, las configuraciones congeladas y los datos crudos de las 90 ejecuciones.

bash

# instalar
python -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt

# validar la configuración sin tocar Docker
python run_experiment.py run --config experiment.yaml --dry-run

# ejecutar y analizar
python run_experiment.py run --config experiment.yaml --analyze-after

bash

# consultar la campaña publicada
python run_experiment.py --db results/final_campaign_20261014/experiments.db list

# regenerar tablas, pruebas y figuras (verifica hashes)
python analysis/final_results.py

# dashboard local
docker compose up -d   # http://localhost:5000
